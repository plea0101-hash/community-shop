## 1. 前端、後端與權限修改面

| 工作面 | 計畫內容 | 不可誤做 |
|---|---|---|
| 前台廠商入口 | 統一「廠商申請」，公司註冊／驗證／加入分店入口明確；登入後才能依權限進入公司與進駐業務 | 不只是把舊停用的 apply 按鈕換字就宣稱完成 |
| 公司／分店後台 | 總部授權、成員／分店管理、負責人交接、分店專屬申請清單、實際品牌＋分店選擇 | 前端角色／URL／任意 branch_id 不能授權；不同統編各自申請 |
| 社區後台 | 資格審查狀態、場地費、設備（沿用上午）、發布／撤下檔期、進駐核准 | 平台審查社區與社區核准廠商分開；available 不等於已發布 |
| 搜尋／公開內容 | 僅顯示核准且有公開檔期者；戶數區間，無戶數篩選／排序；不回傳私密欄位 | 不把 raw households 送到瀏覽器後才遮字；不能用已預約日曆當可招商供給 |
| 預約／取消 | 重用 public.bookings 與 [) 約束，新增分店／約定費快照；社區核准、取消／重新申請／颱風查核接正式 RPC | 不新增第二套庫存、不直接改期；不把線上付款當核准必要步驟 |
| 完成認定 | 社區結束後確認入口；未操作且無取消／爭議／異常，滿12小時自動認定；記completed_at、方式及操作紀錄 | 不立即完成、不前端自報時間、不重複認定；爭議解除等例外先確認 |
| 財務／發布限制 | 顯示每案服務費、週結單／期限、線下收款與人工對帳；發布入口伺服器檢查帳款限制 | 不串支付閘道、不代收場地費／賠償、不用「停帳」取代只擋新發布 |
| 信用／通知 | 取消紀錄、人工違規／申訴／撤銷、颱風事件、帳款與發布狀態通知，重要操作稽核 | 不自訂罰分／停權門檻；入 outbox 不等於 email/SMS 已送達 |

### 公司與授權交易（候選設計，待確認後實作）

- 正規化統編、公司與唯一主帳號由 DB 約束及交易保護。兩個同時申請同統編只成功一個；重試 idempotent，不以瀏覽器查重作唯一保護。
- 先有 Auth 身分不等於總公司已驗證；公司申請、驗證證據狀態、可信主帳號、分店加入同意分開。身份資料最小化／私密儲存／保存期限先確認，不把真實證件或金鑰放聊天或測試。
- 分店員工只能處理被授權的實際分店；總部才有已確認的管理能力。每個申請／核准 RPC 重新驗 company/branch/brand/venue 的關係，不信任 client 自報 tenant。
- 負責人／成員變更用伺服器交易與稽核，防止並行出現兩個有效主帳號；舊權限不能因舊 JWT 還有效就繼續使用。生效／同意程序依 Q-COMPANY/Q-BRAND 定稿。
- 原 brand-members 草稿須接到同一權威成員來源，不能保留一套寬的舊授權，造成新分店 RLS 被 OR 旁路。

## 2. RLS、權限及 SECURITY DEFINER — 先提案，不執行

| 端點／資料 | 授權方案 | 要先通過的測試 |
|---|---|---|
| 公開社區／可招商檔期 | 候選為審查過的最小公開 RPC／projection：只返回允許欄位、戶數區間，強制核准＋已發布條件；無 private households sort/filter | 直接 API、select=*、任意 filter/order、錯誤／匯出／快取皆不得出 raw 精確戶數或私密聯絡 |
| 原 communities 表 | 不能只加 projection 卻繼續允許原表精確欄位公開讀。提出前端改接與原表 SELECT／欄位 grants 的最小切換方案 | 舊主站相容性、anon/auth 矩陣、非目標權限保留；不能先撤舊權限再讓首頁壞掉 |
| 公開 projection 的技術選型 | SECURITY INVOKER view 需要底層權限，不能在撤 raw 權後假設仍能讀；可選固定欄位的受限 definer RPC 或經審核 view owner／barrier 設計 | 底層 row／column privileges、owner/BYPASSRLS、函式 EXECUTE、無動態SQL、row eligibility 都獨立測，不以「有RLS」當保證 |
| 私密地址／聯絡 | 登入＋具體公司／分店／社區授權＋進駐核准狀態；獨立端點／私密資料，不直接 grant 給所有 authenticated | 他公司／同品牌不同分店／離職者／待審案不可讀；取消後期間等依 Q-PRIVACY 定義 |
| 公司／成員／主帳號 | server check 與 RLS 租戶隔離；總部授權及負責人交接的單一交易與不可由 client 指定 actor 的稽核 | 假冒總部、自授權、重複統編、並行加入／轉移、舊session撤權 |
| 預約／社區核准／取消 | 保留 venue→booking 鎖順序與 GiST 最後裁決；新 branch 關係、價格／條件快照與審核前置條件 | 同時預約／核准／取消、重放、租戶隔離與異常回滾，不復活已取消案 |
| 結算／收款／調整 | 僅平台受授權管理入口，社區只能看自身帳；收款自報不等於平台已確認。精確金額、去重與追加式調整紀錄 | 重跑週結／延遲／部分收款、跨社區讀寫、社區偽造paid、金額被client篡改 |
| 新檔期發布 gate | 在受控發布 RPC 內依應收／截止時間與核准規則重驗，不只disable按鈕；只針對新發布 | 逾期 =15 不誤擋、>15 擋新發布；既有confirmed不變、併發付款／發布一致性 |

戶數禁止篩選／排序也包括平台提供的區間查詢面；table-returning RPC／泛用 view 可能仍被 PostgREST 套用輸出 filter/order，不能只移除輸入參數就認為已限制。後續可採固定 JSON 回應或受控端點，只接受核准的地區／場地／時間查詢，不提供戶數或區間排序／篩選。公開區間仍可被外部下載再處理，不宣稱能禁止第三方的本機排序，也不因此回傳精確值。

所有未來 definer 都須固定 search_path、完整 schema 名稱、型別化參數／白名單、最小回傳、可信 actor／組織來源與明列 EXECUTE。RLS 舊 permissive 規則可能 OR 放寬，須同時審查必要 restrictive guard 及已存在 helper 本文。

目前 service_role 對 bookings 的 SELECT/INSERT/UPDATE/DELETE=false，**本計畫不建議補 ALL 或順便補 DML**。新工作可經另行審核的最小 RPC 權限設計處理，不把 service-role key 放前端。定時／人工批次執行身分、函式授權與部署另提確認；平台初期收款走人工紀錄不等於能繞過資料庫權限。

這些新增資料／端點／權限都是新核准範圍，不包含在階段 A 的 bookings TRUNCATE 最小撤權。B 仍 blocked，不拆成 postgres-only defaults 來啟動新業務。

## 3. 分階段順序與預估工作量

估算為**單一負責人**的專注人日（開發、測試、文件合計），不是新增其他審核人。本輪已補上午申請資料範圍，但必填、查驗及交接／爭議邊界仍未定，因此是規劃區間而非工期承諾；外部核驗服務、平台權限、人工決策／staging／法務或其他適用外部要求的等待時間不計。最新約66–100人日（營運／年度需求比前輪50–75增加16–25，詳營運設計第9節），若每週5個完整人日約14–20週；本人兼營運／審查會增加曆時，不保證日期。

| 階段 | 內容／交付 | 前置條件與邊界 | 人日 |
|---|---|---|---|
| P0 規則及安全基準 | 定稿 Q／M 項、欄位與查驗細節、狀態／授權矩陣；A 的獨立核准備件與 B 支持管道評估 | 本輪只完成分析；不把商規確認當 A/B/migration 核准 | 5–8 |
| P1 公司與身份權限 | 公司／主帳號／驗證流程、分店加入與總部管理、品牌關係、審核與稽核，local schema/RPC/tests | 統編／跨公司關係、身份資料規範確認；舊 brands 無法自動猜公司 | 10–15 |
| P2 社區、發布與公開隱私 | 社區申請／審核到正式社區映射、可信社區管理員、設備沿用、場地費與供給視窗、公開RPC／戶數區間 | 欄位／設備細節、交接三天起算與區間端點須定稿；精確戶數曝露路徑的修正方案優先審查，另行權限核准 | 16–24 |
| P3 預約與履約 | 品牌＋實際分店、價費快照、社區核准／私密聯絡、正式取消／颱風與重申請、人工／12小時自動完成與稽核 | 單一bookings／舊案缺欄策略、線下付款例外、異常／完成後處理及隱私政策確認 | 11–17 |
| P4 場地服務費營運 | 精確金額規則、逐案最低、週五09:00按completed_at結算上一完整週（Asia/Taipei）／下週二23:59前付款、人工收款／分配、>15天發布限制與對帳／通知 | Q-FEE/PERIOD/EFFECTIVE/OVERDUE/COMPLETE 確認；不串線上支付、不替雙方退款賠償 | 14–21 |
| P5 整合與營運準備 | 公司／分店／社區 E2E、信用人工查核／申訴、通知重試、權限／並行／財務回歸、staging與單人營運runbook | staging／migration／上線各有獨立核准，適用獨立人工要求不得由AI豁免 | 10–15 |

公司／隱私的急迫小項可先在 P0/P1 設計，但不能把純 UI 遮蔽當完整資料防漏。P2 的基本發布能力先上本機測試，P4 才連上財務發布限制；正式環境不在 gate 尚未完成時假裝符合完整商規。

每階段後先交本機／staging 證據與修訂 migration 草稿，再由本人分事項簽認；本輪結束即暫停，不開始 P0/P1 實作。

## 4. 測試計畫（尚未新增／執行）

| 類別 | 必測案例 |
|---|---|
| 金額 | 免費=0；付費50/500/1,000均按逐筆最低；1,500=150；1,001→101、1,009→101、1,501→151；整數結果不多加1；兩筆1,001各進位101再加總202，不得合計後進位201；每筆先套最低並無條件進位至整數元；精確decimal、不用binary float；第一階段註冊／媒合費均為0；核准時雙方確認最終費為基數，平台費含稅不另加5%；開票／折扣變更仍待確認 |
| 完成／週結 | pending/confirmed或只過end_time不自動算完成；完成／取消／爭議區分；上一完整週一00:00含／下一週一00:00不含，週末包含；跨週／月／年與UTC轉臺灣時間；週五09:00／下週二23:59前付款已確認；人工及12小時自動認定、completed_at歸週；批次重跑／補跑／失敗恢復不重複收費 |
| 逾期與發布 | =15與>15邊界、時間／日曆算法依確認；部分／補款／爭議及恢復；只擋新發布，已核准活動與其通知／接洽不被意外取消或封鎖 |
| 統編／公司 | 同統編同時申請、重試、主帳號唯一、不同統編各自申請、未核驗總部不得取得審核後能力 |
| 分店／帳號 | 自註冊不自動加入，拒絕／撤銷／偽造總部、同品牌跨公司越權、每案品牌與實際分店必填／關係合法；負責人交接與舊token權限撤銷 |
| 社區／檔期 | 未核准／無公開檔期不得搜尋，available不能代替已發布；過期／撤下依政策；社區只能決定自己的場地／案件 |
| 精確戶數／聯絡資料 | API、select=*、filter/order、錯誤、快取／匯出均無精確戶數；無戶數排序／篩選；區間100/101/200/201等端點依定案；未授權或未核准拒讀詳址／聯絡 |

| 通知／營運 | 收件租戶正確、無收件者仍留outbox、重試不重發、入庫/送達/已讀分開；帳單更正與申訴可追溯；無外送服務時不宣稱已送達 |

## 5. 主要風險與回滾方式（僅方案）

| 風險 | 保護／後續核准重點 | 回滾邊界 |
|---|---|---|
| 精確戶數／私密資料已可經原API取得 | 公開投影與原表權限一起審，更新前端／快取（若有），測試所有API路徑 | 不把退回舊版洩漏API當一般回滾；先停用新顯示功能或採審過的安全降級，不能保證追回已下載資訊 |
| 新組織模型造成跨租戶權限 | 法律實體／品牌／分店分離，既有品牌／預約只人工對應，不按名稱推定；單一權威membership | 先停新寫入，保留稽核與舊案，不drop有使用資料的表／欄，不回復已撤的授權 |
| 改動庫存或狀態導致超賣 | 保留唯一bookings與原排他約束，新增分店／條件為附屬資料；確認／取消一致鎖順序 | 停新申請／發布不動已核准活動；不移除約束或回填假confirmed |
| 財務錯算／重複清算 | 費用／政策／履約快照、精確金額、逐案最低、唯一line key及去重，入帳／更正稽核 | 暫停新結算／對帳寫入，追加更正／沖銷事件並經確認，不刪帳或改已出帳金額掩蓋問題；舊30%不自動恢復 |
| 逾期 gate 擴大影響已核准 | 僅在新發布入口檢查，付款狀態與預約狀態分離 | 依另審處理暫停新判定／修正誤判，保留來源；不取消活動或為方便整體開放未付者 |
| A未核准、B無平台權限／新表default仍危險 | 舊限制有效；新表必有各物件最小ACL審查及同交易保護，但不當作B已修；風險接受另簽 | 不自行拆B／提權；不以rollback恢復客戶端TRUNCATE或補service_role DML |
| 定時／人工營運失誤 | 批次可試算／重跑、狀態可觀察、單人分項決議及記錄；何者自動化／手動另確認 | 正常失敗不等於恢復危險權限；保留失敗批次與outbox，按具體核准修復 |

未來 schema 採 additive／expand-contract 設計，先附加欄位／表與版本化端點，再驗證／切換；舊資料只標資訊不足。回填、刪欄或約束收緊都需獨立方案與確認，不在此次產出 migration，也不執行任何正式修改。

## 6. 距離正式商用仍缺的必要條件

- 公司／統編主帳號、首次核驗、總部分店授權／交接、真實品牌＋參與分店的完整流程。
- 社區申請到核准社區的可信映射與管理權、上午資格／設備規格、真正可發布的供給檔期及社區核准。
- 全部公開路徑的戶數隱私、核准後私密聯絡授權及個資儲存／保留與服務條款。
