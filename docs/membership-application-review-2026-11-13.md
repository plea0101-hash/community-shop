## 2. 已確認制度與缺漏

- 第一階段：平台管理員、每社區一名正式社區管理員、正式公司／商業且有統編的廠商會員。一般住戶不需註冊；不開發住戶會員、社區公告推播、住戶購物或線上訂單。住戶活動通知由社區既有管道負責；預約雙方業務通知另保留。
- 社區申請送出不是核准；平台可通過、拒絕、要求補件並留審核紀錄。核准前不得管理場地／發布／審核進駐。缺完整入口、資料分層、佐證、補件、跨申請審核讀取與可信community映射／授權交易。
- 同一社區同時最多一名正式管理員；同名申請不授權。缺交接申請、三天審核異議期、爭議凍結、原子撤舊授新及權限稽核。三天不是自動核准；新申請者期間只讀自己進度／補件。爭議可凍結舊管理員相關權限，不自動取消已核准活動。
- 廠商入口「廠商申請」；有統編且正式登記才可申請會員。自動檢查統編／公司商業登記，異常或無法核實轉人工；首次公司主帳號另驗代表權。基本身分審核通過才可申請進駐。缺驗證提供者、流程、公司唯一主帳號／認領與申訴。基本登記審核不代表食品、商品品質或合法性認證。
- 公司可多品牌／多分店／各自登入；分店加入需總公司授權，撤銷即停止範圍權限。缺公司／分店權威成員來源、管理頁、負責人變更驗證、跨分店隔離。
- 每次進駐追溯公司、品牌、實際分店、操作人與時間；平台會員資格與社區每場審核獨立。缺正式進駐審核RPC及畫面；三種基本UI狀態為待確認／核准／拒絕。public.bookings仍唯一正式預約庫存，DB mapping須另審。
- 費用申請前公開最終總額、核准後不另加未揭露費；平台向社區依核准時雙方確認費計10%最低100並進位，含稅不另加5%。缺約定快照、收款回報、爭議／帳款、平台確認欠款及新申請限制。一般未付款不等於正式爭議，也不能只憑社區報告停權。
- 已確認廠商欠款只限制新進駐申請，既有核准活動不自動取消；清償／爭議妥善處理經確認才解除，保留申訴。與社區欠平台費>15天只限新發布的規則分開，不能混用。
- 既有精確戶數公開讀／顯示、搜尋沒檢查發布檔期，以及模擬付款才確認的舊流程仍衝突；文件更新沒有修復程式或正式風險。

## 4. 建議畫面流程（規劃）

1. 社區：建立帳號／登入 → 社區申請資料與儲存草稿 → 提交 → 自己的待審／補件進度 → 平台通過後社區管理首頁 → 場地／設備／費用設定 → 公開檔期。未核准只可申請業務，不可進正式管理。
2. 平台社區審核：申請清單 → 私密佐證 → 通過／拒絕／要求補件＋理由 → 審核紀錄；通過建立可信社區關聯及唯一正式管理員，不以owner_id直接開權。
3. 交接：新管理員申請／佐證 → 三天審核與異議進度（只有自己申請／補件） → 平台處理異議／必要時凍結舊者相關管理權 → 驗證與異議完成後明確核准 → 同交易撤舊授新 → 歷史紀錄。已有活動持續，必要營運代辦權限另確認。
4. 廠商：入口「廠商申請」 → 帳號／公司統編登記查驗 → 代表權驗證 → 正常自動檢查／異常人工審核進度 → 基本資格通過 → 公司品牌／分店管理；既有稅號進認領／異常流程，不能搶占或覆寫。
5. 分店：自註冊 → 申請加入公司 → 總公司查核授權 → 分店範圍啟用 → 總公司撤權／負責人變更驗證／歷史。不能只因email或品牌相同自動加入。
6. 進駐：核准廠商 → 公開檔期／最終費用 → 品牌＋實際分店 → 待確認 → 所屬正式社區管理員核准／拒絕 → 核准後授權詳址／聯絡；付款原則活動結束時現金／轉帳給社區 → 收款狀態／爭議 → 完成／週結／必要欠款審查。平台會員審核與場次核准各有獨立狀態。

[上傳畫面、安全與測試專案設計](community-document-upload-design.md)列文案、虛構示意、私人儲存／存取、格式容量候選與U01–U05待確認事項。M01不再將草稿能力與兩類證明必備列為待決；其餘必填、充分性、具體格式／容量、客服／保存與查驗仍待定。原申請表並無已證實文件上傳功能，計畫不代表已完成；不改SQL或權限。

## 9. 社區年度重驗與營運參數增量

[營運後台／年度驗證設計](operating-policy-revalidation-design.md)為單一規格：每12個月確認社區管理資格及授權，週期未來由授權後台調整；系統提醒／收件／補件／初檢分類，異常及需複核人工處理。保留聲明、文件版本、查驗依據、分類／決定與完整actor／時間。有效期內文件不保證授權仍在，也不能將系統無異常分類當正式通過。

管理員、主任委員或授權關係異動立即觸發重驗。原單管理員／交接三天不自動轉權／爭議凍結規則保留；年度案綁任期／授權版本，提交重驗權限，不讓舊任期替新者通過或自動讀他人證件。

正常案完成方式、到期未完成的權限限制、提前提醒與頻率均未定；30／14／7天只是建議。年度基準／時區／月底、授權撤銷與交接並行、證據保存充分性列O清單，不自行套停權。三頁流程與測試詳設計第5／8節。新增候選revalidation_cases附於既有社區／任期並引用原私人文件，不新建平行會員／預約來源，現有repository尚無正式年度流程。

最新分期工作量66–100專注人日（相對50–75增加16–25）；第6節原階段基線供歷史對照，現行各期以實作計畫與營運設計第9節為準。沒有新增功能測試、SQL或正式排程。
