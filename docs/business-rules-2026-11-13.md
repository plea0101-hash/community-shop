## 1. 版本及優先序

- 本輪 10%／最低 100 規則取代先前 30% 決策。現有 repository 找不到 30% 計算程式或規格，因此不能聲稱已替換了既有收費實作；目前沒有收費引擎。
- 本輪「初期不處理線上金流」取代舊原型「模擬付款才確認預約」的產品假設。不能因此把未審的 `payment_reviewed` 開關改 true；須先確認線下付款／爭議邊界。
- 舊版一般取消 ≤24 小時、先取消後重申請及不自訂處罰仍有效；颱風的新「當日機制、不計違規」不自動放寬成無公告／無查核的永久豁免。
- 上午設備、社區申請與資格規則沿用原確認版本，不以 demo seed、目前表欄位或本輪推測替代。完整版本目前未在取得的文件／分支找到，列 Q-MORNING。
- 本輪只產出規格與計畫。任何 schema、RLS、definer 或應用實作另待確認，正式執行更需獨立核准。

| ID | 規則 |

| F02 | 免費場地的平台費為 0；不能套最低 100 |

### 邊界與不可混用

- 社區收取的場地費、廠商→社區的付款，以及社區→平台的服務費應收，是三個不同概念，資料與顯示分開。
- 未付款、未核准、活動時間已過，不可自動等同「案件已完成」。完成認定需明確流程，才可入週結。
- 不自訂逾期罰金／利息／催收費、不凍結全帳號、不取消已核准活動。15 天限制只用於新檔期發布，不拿來當取消處罰門檻。
- 已發布但未核准的檔期、修改／延長／重發與恢復發布的邊界未確認，不自行擴大限制。

## 3. 廠商與公司 — 已確認

| ID | 規則 |
|---|---|
| C01 | 前台入口統一「廠商申請」；登入後公司／分店管理、進駐業務仍清楚區分 |
| C02 | 一個統一編號僅一個公司主帳號；不同統編分別申請，不把不同法律主體合併成同一公司 |
| C03 | 總公司首次申請必須完成身分驗證；不能僅憑可登入或 email 相同即通過 |
| C04 | 分店可自行註冊，但加入公司要總公司授權；未授權不能取得公司或品牌業務權限 |
| C05 | 總公司可管理分店、帳號及負責人變更；重要授權／變更保留操作紀錄 |
| C06 | 分店可獨立管理其進駐申請；每筆必填品牌與**實際參與分店**，由後端驗證關係 |

認證使用者、公司、品牌、分店為不同實體。不能把品牌名稱／聯絡資訊當法律公司或授權，不能把統編唯一約束套在每個分店的登入帳號而禁止合法分店加入。

不同統編仍須分別申請；總公司跨不同統編子公司／分店的管理，必須有明確的公司間授權設計，不能藉「加入公司」跳過 C02。品牌授權／加盟關係與跨公司權限細節待確認。

## 5. 取消、信用及颱風 — 已確認與沿用

| ID | 狀態與規則 |
|---|---|
| X01 | 沿用一般取消：雙方可取消，釋出時段；不直接改期，取消後重新申請 |
| X02 | 沿用距原活動開始 ≤24 小時為臨時，>24 小時一般；臨時原因必填，留 actor／時間／原活動／理由／狀態及對方通知 |
| X03 | 臺灣任一縣市政府宣布因颱風停班或停課，啟動當日特殊取消機制，不限雙方所在地；「停班停課」與先前已確認的停班**或**停課一致，不改成必須同時具備 |
| X04 | 當事雙方自行決定是否取消，不自動取消全部預約；保留官方來源、公告日期、適用日期與查核歷史 |
| X05 | 符合且已核驗者另列颱風取消，不計一般臨時取消次數；不能驗證維持待審，待審不先算違規，確認不符才依原 timing 分類 |
| X06 | 平台管信用／違規紀錄，不直接裁處或處理雙方賠償；沒有已確認的自動取消處罰門檻 |

臨時取消次數是事實統計，不自動等於已成立違規或信用扣點；成立、申訴與處置規則仍須確認。本次再次確認：符合官方公告適用日的當日颱風取消不計違規；不得新增例外扣點或拒絕豁免。退款責任仍待確認。公告日不等於適用日；當日按臺灣日期處理。跨日、補登、事後公告與付款／退款例外見待確認，不由本文件自行決定。
