# 預約取消：架構檢查與實作計畫

## 檢查結果（2026-11-13）
- 基底：68759ce，純 HTML/JS；沒有套件、CI、migration 或正式身分驗證流程。
- index.html 以公開 publishable key GET communities、venues。available() 永遠 false；apply/admin 導覽停用。
- 舊 bookings/applications 只是本機 state；cancelBooking 沒有授權、伺服器時間、取消原因或通知，不適合正式使用。
- 唯讀 Data API 檢查：communities/venues limit=0 回 200；bookings 回 401 / 42501（anon 無 SELECT）；applications/profiles 回 404。OpenAPI 回 401，要求 secret key。本工作不索取或使用 service-role key，也不探查真實預約內容。
- 無法確認 bookings 欄位、現有 Auth 對應、RLS、鎖定時段及建立預約程序。需要去識別化 schema 才能安全完成正式資料串接。

## 編碼前計畫
1. 獨立分支新增 /cancellation/ 管理頁，不改正式首頁、不部署。用 Supabase Auth 登入；角色由伺服器判斷，無前端角色授權。
2. 純函式處理時間差、分類、統計；臨時取消門檻未確認時保留 NULL / unclassified，不設定處罰。距開始時間使用原始精度，臺灣日期以 Asia/Taipei 計算。
3. SQL 草稿以獨立 cs_ 表與 RPC 建模：預約/時段、雙方會員、管理員、不可改寫取消快照、官方公告及審核、通知。交易鎖與唯一性防重複取消；取消釋放模組內原時段；重新申請建立新預約，不提供改期。與正式 bookings 的映射尚待 schema 確認。
4. 雙方各有我的預約、確認取消、原因、紀錄、通知及重新申請入口。管理頁包含日期/取消者查詢、臨時取消統計、颱風核驗與頻率排名。未驗證的颱風主張暫不計違規，審核拒絕後依原時間與門檻分類。
5. 任一臺灣縣市官方因颱風停班或停課且適用日涵蓋活動日即符合特殊事件；不比對雙方所在地，不自動取消。審核需保留來源、公告日、適用日、停班/停課與颱風依據。URL 是證據而非自動核驗，須管理員人工查核。
6. 合成資料單元測試、瀏覽器整合測試、隔離 PostgreSQL 交易/RLS 測試；不對遠端執行 SQL 或寫入測試。完成後建立 PR，不合併、不部署。

## 完成的必要條件與邊界
- 正式 migration 僅為草稿，不在自動執行目錄。正式 schema 整合、門檻確認、Auth 帳號/權限配置、通知外送服務必須另行確認。
- 頁內通知於取消交易內寫入對方收件匣；外部 email/SMS 不假裝已送達。
- SQL 測試只能在一次性本地資料庫；不連線 Supabase 寫入。沒有實際官方公告與真實預約作測試。

## 使用者確認（編碼期間）
臨時取消為距開始 <=24 小時，一般取消 >24 小時。SQL 初始政策採 24；NULL 僅作缺少政策時的安全退路。颱風已核驗另列且不計一般臨時取消次數；僅供人工查核，沒有自動處罰。
